# 06 业务流程与状态图

> **给谁看**：研发、新人、评审会 ｜ **什么时候用**：理解流程、讨论改动、排查问题
> **一句话**：四张图讲清「一次研究从提交到报告的全过程」。

## 图 1 主研究流程（assets/main.png）

三段结构：**启动准备**（记忆注入 → 会话上下文 → MCP → 预算护栏 → 规划 → 看板）→ **主循环**（至多 20 步：注入进度看板 → 调用模型 → 四级出口判断 → 工具执行 → 危险确认 → 回填 → 熔断 → 下一轮）→ **收尾兜底**（五出口汇合 → 强制结题 → 笔记兜底 → 记忆与日志 → 报告推送）。

看图要点：
- 四级出口判断按代码顺序排列：无 tool_calls 且正文有效（model_done）→ 预算 95% 硬收尾 → 上下文超限压缩 → 执行工具
- 熔断指令必须在回填之后注入（否则破坏 tool_call_id 配对）

## 图 2 运行状态机（assets/runstate.png）

| 状态 | 含义 | 转出条件 |
|---|---|---|
| PLANNING | 规划中 | 大纲与看板就绪 → RESEARCHING；规划失败降级空大纲 → WRAPPING |
| RESEARCHING | 主循环研究 | 模型完成/预算95%/步数耗尽/用户中止 → WRAPPING；协议错误 → ERROR |
| AWAITING_CONFIRM | 危险工具等待确认 | 批准 → RESEARCHING；拒绝/超时(600s) → WRAPPING |
| WRAPPING | 收尾兜底 | 报告定稿（兜底链保证非空）→ REPORTING |
| REPORTING | 记忆与日志 | final 推送 → DONE |
| DONE / ERROR | 终态 | — |

## 图 3 子问题看板状态机（assets/board.png）

待查证 → 查证中 → 已完成。两条核销路径：note_write 内容命中「子问题 X」标记自动核销（附笔记首句作为结论摘要）；update_checklist 显式核销。全部核销 → 下一轮注入强制收尾提示。

## 图 4 评测六步流水线（assets/evalflow.png）

取题（问题+key_points）→ 真跑（生产内核标准档）→ 截留证据池 → judge 对照阅卷（JSON 四维分+issues）→ 聚合 → 成绩单落盘。详见 [05-评测规格](../01-定义层/05-评测规格.md)。

## 串行关系要点（易误解处）

- 大纲是「一次生成、三处落地（system prompt/看板/事件）、逐轮演化、全绿触发终局」的单一数据源
- 子问题的查证顺序是模型自主调度（看板全可见），通常按 id 顺序但允许乱序与批量核销
- 与多智能体的区别：大纲模式共享一切串行执行（子问题无独立循环）；多智能体隔离一切并行执行（见 stages/07，未接入工作台）
