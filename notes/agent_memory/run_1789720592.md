Anthropic《Effective context engineering for AI agents》(anthropic.com/engineering/effective-context-engineering-for-ai-agents)：
- 术语演进：从 prompt engineering 到 context engineering；后者指在 LLM 推理期间策展与维护最优 token 集合（含系统指令、工具、MCP、外部数据、消息历史等）。
- 核心心智模型：把 context 视为有限资源/注意力预算(attention budget)；LLM 会出现 context rot / 注意力稀释，越长的 context 每个元素占比越小。
- 目标：find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome。
- 关键技巧：长任务用 compaction（压缩总结）、设计 token-efficient 工具、让 agent just-in-time 探索环境(而非预载全部数据)。
- 趋势判断：更强模型需要更少的 prescriptive engineering，agent 自主性更高。
- 作者：Anthropic Applied AI team（Prithvi Rajasekaran 等）。

PM 学习清单素材A｜评测(evals)能力（来源：woshipm.com/ai/6372714.html）
- 观点：Agent 时代，AI PM 最重要能力从"原型/功能设计"转向"评测体系设计/质量系统构建"；模型/提示词/知识库/工具/权限都在变，传统灰度反馈兜底失效。
- 微软信号：2026-02-03 微软 Copilot Blog 发文讲如何评测 AI agents；2026-03-18 Copilot Studio 2026 release wave 1 把 support for evaluations 与治理能力放入主叙事，生产部署自 2026-04-01 开始。
- AI 产品三问：真实场景好不好用？哪些场景会失控？每次更新后是变好还是悄悄退步？
- 传统指标（点击率/留存/会话时长/满意度）不够：只能看结果层，AI 失败常是"局部失败"。
- 4 层评测框架：①结果质量 ②任务完成度（是否真做完，如摘要/填表/带到下一步）③工具与流程正确性（是否调对工具、顺序对、该升级人工时升级、该停则停）④安全与权限边界（带身份上下文，否则"假高分"）。
- 评测从场景开始而非指标：先定 scenario 和 scope → 找高价值场景 → 补真实表达（模糊/混合意图/半截问题）→ 每类场景定义成功标准。
- 上线前4件事：选 20-50 个高价值真实场景做最小测试集；每场景定义通过标准；至少配置 3 类评分逻辑（质量/能力/工具流程）；用不同身份跑一遍验权限边界。
- 上线后3件事：改提示词/模型/知识库/工具后跑回归；看失败是否集中在高风险场景（模式>个案）；评测结果接入迭代优先级。
- 结论：PM 角色更像"AI 质量设计者"，竞争力从做功能转向做可信的能力系统。

PM 学习清单素材B｜Evals 实操（来源：hub.baai.ac.cn/view/48381，转述 Aman Khan 博客）
- 论点：Evals 是唯一能拆解系统每一步、精确衡量单个变更影响的方法；"写 Evals"正成为 AI PM 的决定性技能（原文称"2025年及以后"）。
- 比喻：评估 AI 像驾照考试——感知（能否准确解读信号并适应环境变化）、决策（未知情况下稳定做正确选择）、安全（始终遵循指令、不出岔子）。
- 与单元测试区别：LLM 系统环境多变、结果不确定（同 prompt 多次输出可能不同），指标偏定性/开放式（相关性、连贯性），难用通过/失败衡量。
- 三种 Evals 方法：①人工 Evals（产品内赞/踩、专家标注，用于 RLHF）——贴近终端体验但反馈少、信号弱、成本高；②基于代码的 Evals（检查 API 调用/生成代码是否可执行）——便宜快，但主观/开放任务信号弱；③基于 LLM 的 Evals（LLM-as-judge）——可扩展性极高、PM 可直接写自然语言评估 prompt、可给出解释；缺点：需少量标注样本校准、概率性、需足够数据量；生产中常用置信度评分或多 LLM 裁判组。
- 四阶段流程：…（初始评估）→ 对比新模型（拿问题集重跑、目标超过基线）→ 生产环境监控（持续评估、对比 Eval 结果与真实用户反馈、构建可指导行动的 Eval 仪表盘）。
- 注意事项：不要起步就设计过复杂（产生噪音、团队失去信心）；要测边缘案例、用少量好/坏小样本提示提升裁判准确率；要用真实用户反馈验证 Eval 结果。
- 起步步骤：选一个关键特性（如幻觉检测）→ 写简单 Eval 检查是否忠实引用 → 在 5-10 个代表性真实交互案例上运行 → 复盘迭代优化 Eval prompt。

Google 白皮书 Day4《Agent Quality》(Google, 2025-11)，经 vanducng.dev/2026/01/13 转述：①传统测试="Did we build the product right?"；AI 评估="Did we build the right product?"。比喻：传统软件=送货车(固定路线/清单式QA)，Agent=F1赛车(需持续遥测判断每个决策)。②Agent 失败是"静默失败"(API 返回 200 OK、输出看似合理但严重错误)。四类失败模式：算法偏见(按邮编过度拒贷)、事实幻觉(编造历史日期却高置信)、概念漂移(欺诈检测漏掉新攻击模式)、涌现行为(钻系统规则漏洞、与其他 bot 打代理战)。③演进复杂度：传统 ML(F1/RMSE 清晰指标)→被动 LLM(无简单指标、概率输出)→LLM+RAG(检索+生成多组件)→LLM Agent(规划+工具+记忆)→Multi-Agent(涌现行为、系统级失败)。④三原则之一：Evaluation as Architecture——"Agent quality is an architectural pillar, not a final testing phase"；设计成"evaluatable-by-design"，从第一行代码起就输出日志与 trace。⑤原则二：The Trajectory Is the Truth(轨迹即真相)——评估的是过程+结果混合体系，并把评估失败回灌到反馈闭环改进 Agent 与评估集。⑥可观测三支柱：Logs(日志=日记)、Traces(端到端请求流=叙事)、Metrics(指标=健康报告)。参考件：OpenTelemetry、Google Cloud Logging、Google Cloud Trace、TruthfulQA、LLM-as-a-Judge(arXiv)、Agent-as-a-Judge(arXiv)。来源 vanducng.dev
