# 05 评测规格

> **给谁看**：研发、测试、未来的自己 ｜ **什么时候用**：每次改动前后的回归、新增能力时扩题
> **一句话**：定义「什么是好」——题库怎么出、四维怎么打分、红线在哪、噪声怎么治。

## 一、评测的目的（为什么做）

三个没有评测就踩的坑：进步无法证明（"感觉变好"不构成验收）；退化无法察觉（改 A 悄悄弄坏 B）；取舍无法决策（workflow/agent/反思哪个好，跑分说话）。
一句话：**没有 eval 的迭代 = 没有验收标准的 PRD。**

## 二、评测的构成（三件套）

| 件 | 文件 | 内容 |
|---|---|---|
| 考卷 | questions.json | 12 题：事实类 6、对比类 4、开放类 2；每题带 key_points（必须查到的要点） |
| 阅卷老师 | judge.py | LLM-as-judge：只对照原始证据核对结论，四维各 0-1 分并附扣分依据 |
| 教务处 | run_eval.py | `--n 3` 快跑 / `--id q02 q07` 指定题 / 全量；成绩单落盘 evals/results/ |

## 三、四维评分标准（rubric 全文锚点）

| 维度 | 定义 | 0 分锚点 | 满分锚点 | 当前基线 |
|---|---|---|---|---|
| supported 有据 | 关键结论均能在原始证据中找到支撑 | 编造/证据不足 | 每个事实有对应证据 | 0.54 |
| sourced 有源 | 每个事实带 [n](url) 引用 | 无引用 | 全文规范引用加参考小节 | 0.83 |
| complete 覆盖 | 问题及大纲要求的信息点全部覆盖 | 缺一半以上 | 全覆盖且逐点查证 | 0.72 |
| concise 简洁 | 无复述原文、无空话套话 | 严重冗长 | 结构清晰、信息密度高 | 0.54 |

**灵魂设计 groundedness**：judge 不上网。它拿到的不是「世界真相」，而是 agent 调研时工具返回的原始证据——评的是「结论是否忠于你自己查到的证据」，专抓编造。

## 四、评测流程（六步）

```
取题(问题+key_points) → 真跑(生产内核, 标准档) → 截留(搜索/抓取返回存为证据池)
→ 阅卷(judge对照: 问题+大纲+证据前12条+报告, JSON输出四维分+issues)
→ 聚合(总分+维度均分+逐题问题清单) → 落盘(evals/results/eval_日期_时间.md)
```

## 五、标准如何定义（业界方法学对照）

业界四层指标体系：任务层（成功率）、过程层（工具调用/步数/指令遵循）、内容层（有据/相关/覆盖/引用）、工程层（延迟/成本/方差/鲁棒/安全）。
本项目四维对应内容层；工程层指标由 RunLog 记录进面板（大节点 12）。
四类评测方法组合：确定性断言（引用有无，代码可判）+ 要点比对（key_points 命中）+ LLM-as-judge（质量类）+ 人工抽查（校准 judge）。

## 六、定义标准的原则

1. 标准从需求来：key_points 就是 PRD 验收条款——评什么，agent 才练什么
2. 标准与核心风险对齐：本项目最大风险是编造 → supported 是灵魂维度；换场景标准体系会不同
3. 可复现：标准写死在 rubric，不凭 judge 心情
4. 标准也要迭代：agent 升级后旧标准失效（如新增会话能力应加「多轮一致性」维度）

## 七、红线与噪声规则

- 回归红线：任何改动不得让任一维度低于基线 -0.05
- 合格线：supported ≥ 0.70（本版目标）
- 噪声治理：单题分差 0.2+ 属正常，**结论只看多题均值**
- 低分三分类处置：系统故障（修评测器/收尾路径）、偶然噪声（重跑不改代码）、真实缺口（进归因流程）
- judge 解析失败记全 0 但必须标注（q10 教训：区分「真差」与「故障」）

## 八、归因口诀

**评测出分数，trace 找病灶，修复下刀要小，回归验证明效。**
评测只给现象（supported 低），不给病因；病因要读 trace 逐环定位（检索到了吗 → 抓到正文了吗 → 萃取留住了吗 → 压缩丢了吗 → 模型引用了吗）。
