# Stage 8 复盘：记忆 + HITL + 护栏（2026-09-16）

## 建了什么
- `common/memory.py`：MemoryStore（注入/提取/合并，容量20条，研究内容严禁混入）
- `common/guardrails.py`：Budget（80%预警/100%强停）+ DANGEROUS_TOOLS 分级 + ask_human
- `stages/08_production/production_agent.py`：三件套集成 + 危险工具 send_report(模拟)

## 四个验收实验
| 实验 | 内容 | 结果 |
|---|---|---|
| A 记忆写入 | 会话中说出偏好 → 结束后沉淀 | ✅ 3条偏好入 memory.json |
| B 记忆生效 | 新会话提问 → 注入+遵守 | ✅ 注入3条，输出自动用表格 |
| C HITL拦截 | "查完发给boss@example.com"+输入n | ✅ 拦截→拒绝→模型尊重决定给替代方案 |
| D 优雅收尾 | LOW_BUDGET=3000 | ✅ 80%时注入收尾，输出阶段性结题报告 |

## 踩坑与要点
1. **记忆提取首跑静默返回空**：无从排查 → 加"提取到N条候选"回显。
   教训：不可观测的环节坏了都不知道
2. **预算的最后一跳**：收尾调用本身耗token，实测4563/3000越过上限
   → 预算判断要给收尾留余量（如触发线设在80%）
3. **拒绝回执的话术设计**：拒绝时不是简单返回"用户拒绝了"，
   而是"不要重复尝试+改为直接输出内容"——回执会进上下文影响模型下一步
4. B实验意外收获：Kimi调研题搜得多触发预算预警，自动输出结题报告——
   三件套在真实负载下自然协作了

## 三件套的统一哲学
记忆兜"理解错偏好"、HITL兜"做不该做的事"、护栏兜"跑飞了"——
共同回答：**agent出错时，谁来兜底、代价多小**
