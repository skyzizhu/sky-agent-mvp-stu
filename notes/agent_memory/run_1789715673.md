Anthropic《Demystifying evals for AI agents》官方原文（anthropic.com/engineering/demystifying-evals-for-ai-agents，Published Jan 09, 2026）：核心定义表——Task(测试用例，明确输入+成功标准)／Trial(一次执行，因输出随机需多次运行)／Grader(评分逻辑，一个task可有多个grader，每个含多个assertions)／Transcript(完整记录：输出+工具调用+推理+中间结果+交互)／Outcome(环境最终状态，非口头回复)／Eval Harness(端到端运行基础设施)／Agent Harness。关键论点：agent 因多轮调用工具、修改状态、适应中间结果，错误会传播叠加；frontier 模型可能用超出静态 eval 的创造性解法（Opus 4.5 在 𝜏2-bench 订机票发现政策漏洞，「判失败」实为更好方案）。

Anthropic 三大 grader 详解（blog.aihao.tw 中文解读，2026-02-17）：①Code-based 代码型：字符串比对、二元测试、静态分析、结果验证、tool call 检查；优=快/便宜/客观/可复现/好调试；缺=对有效变体脆弱、抓不住细微差别、主观任务有限。②Model-based 模型型(LLM-as-judge)：rubric 评分、自然语言断言、成对比较、多评委共识；优=灵活可扩展、适合开放式/自由格式输出；缺=非确定性、贵、需持续与人类校准。③Human 人工：专家审查、众包、抽样检查、评分者一致性检验；优=金标准、用于校准前两者；缺=贵慢、需领域专家。实务几乎都混搭：coding agent 用确定性测试，对话 agent 更依赖 LLM judge，所有类型都需偶发人工抽查。

Anthropic 评估框架其余要点（blog.aihao.tw）：①Capability eval vs Regression eval 两类目标不同——能力评估(难题、低通过率、推动变强) vs 回归评估(应近100%通过、防改A坏B)，混看会误判。②按 agent 类型定策略：Coding(SWE-bench Verified、Terminal-Bench、确定性 grader)；Conversational(第二 LLM 模拟用户，评 ticket解决/轮次/语气/合规，τ-Bench、τ2-Bench)；Research(groundedness/coverage/source quality 检查，BrowseComp)；Computer Use(真实或沙盒跑，验 URL/页面/后端状态真值，WebArena、OSWorld；DOM vs screenshot 取捨)。③非确定性处理 pass@k(至少一次成功，k越大越高) vs pass^k(全部成功，k越大越低)，k=1相同 k=10截然不同；一次成功够用(pass@k)，要求稳定(pass^k)。④有效 eval 好处：提前发现 regression、逼团队定义成功、加速模型升级(days vs weeks)、建立延迟/token/成本基准；案例 Claude Code、Descript、Bolt。

三类 grader 选择策略（来源 iceyao.com.cn / memexlab.ai）：Code-based=有客观标准任务（字符串/JSON schema/单测/静态分析/状态检查/transcript统计），快、便宜、可复现、第一道防线，缺点是过刚会惩罚合理变体（CORE-Bench 案例：浮点四舍五入被拒）。Model-based(LLM judge)=开放式/主观质量（完整性、语气、研究报告覆盖、代码可维护性），须给结构化 rubric、允许 Unknown、要求引用证据，且必须与人工评分校准。Human=高风险/校准/仲裁，不评全部样本，用于抽样校准 LLM judge、分歧仲裁、新 rubric 专家标注。建议混合搭配而非只选一种。

## 15:19:45
capability vs regression eval（来源 iceyao.com.cn / memexlab.ai）：Capability eval 探索能力边界，起始通过率低（目标是暴露做不好的地方），含真实失败案例、长链路多工具任务；Regression eval 守门，保住已有能力不退化，稳定任务从 capability suite "毕业"进回归集。起步建议：从真实失败案例挑 20–50 个任务，遵循 80/20 法则（少量精选任务早期收益最大），成熟后扩展。非确定性指标：pass@k（k次至少成功一次，k越大越高）、pass^k（k次全成功，k越大越低，衡量次次靠得住）。pass@100=0% 通常说明任务定义模糊/评分器太严/环境拦掉正确解法，应先复核任务规格与评分器，而非直接归因模型能力。
